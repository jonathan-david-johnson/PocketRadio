# Remote Presence Asymmetry Bug

**Date:** 2026-06-28  
**Branch:** remoteplay (iOS), remoteplay (menubar)  
**Status:** Under investigation

---

## Observed Behavior

Two-device test: iOS simulator + macOS menubar, same Supabase userId, same channel `remote:{userId}`.

| Direction | Works? | Evidence |
|-----------|--------|----------|
| Mac sees iOS presence | ✅ Initially yes (image 10: "17 Pro - No Watch (Paused)" in Mac picker) | — |
| iOS sees Mac presence | ✅ Yes (after `x-user-uuid` header fix: iOS selected "Jonathan's MacBook Pro") | "▶ Playing on Jonathan's MacBook Pro" shown on iOS |
| Mac receives `load_station` command | ✅ Yes (KCRW started playing on Mac) | — |
| Mac picker shows iOS devices | ❌ No — "No devices found" after menubar rebuild | image 11 |

Current asymmetry (post `x-user-uuid` fix): **Mac cannot see iOS in presence list**, even though iOS can see Mac and the Supabase channel is shared.

## Architecture

### iOS (Supabase Swift SDK)
- Uses `supabase-swift` package (Realtime v2)
- `channel.track(RemotePresence)` — SDK handles wire encoding, `phx_ref`, JWT auth
- `channel.presenceChange()` async stream — SDK decodes `presence_diff` / `presence_state`
- Auth: anon key as `supabaseKey`, `x-user-uuid` header via `SupabaseClientOptions`
- Presence decode path: `presenceV2.state` (`JSONObject` = `[String: AnyJSON]`) → `JSONEncoder` → `JSONDecoder` → `RemotePresence`

### macOS Menubar (raw WebSocket)
- Hand-rolled Phoenix v2 WebSocket — no Supabase Swift SDK
- Wire format: `[joinRef, ref, topic, event, payload]` JSON arrays
- Auth: anon key as `apikey` header + `Authorization: Bearer {anonKey}` header + `access_token: anonKey` in join payload + `x-user-uuid: userId` header (added 2026-06-28)
- Presence track: sends `["presence", {"type":"presence","event":"track","payload":{state}}]`
- Presence decode: parses `presence_diff.joins[key]["metas"][0]` → `JSONSerialization` → `JSONDecoder` → `RemotePresence`

## Root Cause Theories

### Theory 1: `presence_state` arrives before iOS connects (most likely)

`presence_state` fires once when the Mac joins. If iOS hadn't joined yet (or re-joined after the Mac), Mac only receives the initial state (potentially empty or only containing Mac itself). Subsequent iOS joins arrive via `presence_diff`, but the Mac's `applyPresenceDiff` may fail to decode them.

**Evidence for:** Mac shows "No devices found" even after iOS is clearly active.  
**Evidence against:** In image 10 (old build), Mac DID see iOS. Something regressed.

### Theory 2: `decodePresence` silently fails for iOS presence format

iOS tracks presence via SDK which may add extra fields (`phx_ref`, `phx_ref_prev`, SDK metadata) to `metas[0]`. If `JSONDecoder` hits a type mismatch — e.g., `playback.state` sent as something the Mac's `PlaybackState` enum can't decode — the whole decode fails and `presenceList` stays empty.

iOS `RemotePlaybackState.state` is `String`. Mac's `RemotePlaybackState.state` is `PlaybackState` (enum). Values: `"playing"`, `"paused"`, `"idle"`. These should round-trip fine.

**What would cause failure:** any unknown enum value in `state`, or nested `playback` object having a different key than `"playback"`.

### Theory 3: Presence key mismatch in `otherDevices()` filter

```swift
func otherDevices() -> [RemotePresence] {
    presenceList.values.filter { $0.deviceId != deviceId }.sorted { ... }
}
```

If Mac's own presence ended up in `presenceList` under the wrong key, and the `deviceId` field inside the decoded `RemotePresence` matched Mac's `deviceId`, Mac filters itself out. This could happen if Mac's `presence_state` includes Mac's own entry AND the `device_id` field inside correctly matches `deviceId`.

**Evidence:** In image 10, Mac correctly showed iOS. After rebuild, it stopped. Rebuild clears channel state and re-joins — might change the presence_state snapshot received.

### Theory 4: `access_token` not a valid JWT (pre-fix theory)

Before the `x-user-uuid` header fix, Mac's join used `sb_publishable_...` (new Supabase publishable key format) as `access_token`. This format is NOT a JWT — it's an opaque API key identifier. Supabase Realtime may silently reject the `presence.track` call server-side because it can't verify the sender, even while still delivering the join OK and distributing other devices' presence events.

**Status:** Partially fixed — adding `x-user-uuid` header may have fixed iOS seeing Mac. But doesn't explain why Mac still can't see iOS.

### Theory 5: iOS presence key vs. `device_id` field mismatch

The Supabase Swift SDK sets `config.presence.key = deviceId` in channel config. The `presence_state`/`presence_diff` dictionary key is this value. If the iOS SDK uses a DIFFERENT key than the one set in config (e.g., a session key auto-generated by the SDK), then `presenceList["sdkGeneratedKey"]` is populated with `RemotePresence(deviceId: "iOSUUID", ...)`. The `otherDevices()` filter checks `p.deviceId != deviceId` (comparing iOS UUID vs Mac UUID — should pass). So this theory doesn't explain "No devices found" unless the presence key matches Mac's deviceId exactly (impossible).

## What Changed Between Working (Image 10) and Broken (Image 11)

- **Image 10** (old menubar build): Mac sees iOS. iOS can't see Mac. `x-user-uuid` not sent.
- **Menubar rebuild** with: `x-user-uuid` header added, `ObservableObject` added to `RemoteControlService`, presence decoding via `applyPresenceDiff`/`applyPresenceState` added, all `print()` → `RemoteDebugLogger`.
- **Image 11** (new menubar build): iOS can see Mac ✅. Mac can't see iOS ❌.

The regression is in the new menubar build's presence decoding. The old build (image 10) somehow decoded iOS presence correctly.

**Old decode path (image 10, before this investigation):**
```swift
case "presence_diff":
    let joins = (payload["joins"] as? [String: Any]) ?? [:]
    for key in joins.keys { print("join device=\(key)") }
    // NO presenceList population — presenceList was always empty
    // But Mac picker DID show iOS...
```

Wait — the old build had **no `presenceList` at all**. The Mac picker in image 10 (`RemoteDevicePickerMacView` wasn't implemented yet). Image 10's Mac picker was something else... 

Actually, re-examining: image 10 shows the Mac's NEW picker (built in this session) showing "17 Pro - No Watch (Paused)". So the new `applyPresenceDiff` WAS working at that point. Then the rebuild (for the `x-user-uuid` fix) broke it.

**Most likely regression:** The `RemoteControlService.stop()` now clears `presenceList = [:]`. When `make menubar` kills and relaunches, the new instance starts fresh and joins the channel. The `presence_state` received may only contain Mac itself (if iOS hadn't re-tracked presence yet). No subsequent `presence_diff` join for iOS arrives because iOS didn't change state. iOS is "already there" from Supabase's perspective, but the Mac missed the `presence_state` that included iOS.

Open menubar's debug window (ⓘ icon, bottom-left) immediately after both apps start. Look for:

1. `channel joined ok` — confirms WebSocket join
2. `presence_state total=N` — if N=0 or N=1 (only self), iOS wasn't in the snapshot

5. Any `presence join device=...` lines for the iOS device UUID

## Wire Contract Reference

`RemotePresence` JSON (from `contracts/remote/presence_ios.json`):
```json
{
  "device_id": "A7525836-E412-4DC3-B8C8-4DD12AE8C986",
  "device_type": "ios",
  "device_name": "Jonathan's iPhone",
  "role": "sender",
  "playback": {
    "state": "playing",
    "station_id": "abc123",
    "station_name": "KCRW Eclectic 24"
  },
  "updated_at": "2026-06-28T01:23:45Z"
}
```

When Supabase distributes this via presence, `metas[0]` additionally contains `phx_ref` (string). Decoder must tolerate unknown keys — `RemotePresence` uses explicit `CodingKeys` so this should be fine.
