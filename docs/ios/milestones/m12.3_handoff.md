## The blocking decision — Up Next as a core destination

The user's instruction: *"Up Next: Let's treat it like we do profile, discover,
etc. It's always going to be either shown or under more."* That means moving
`.upNext` out of extra and into `TabDestination.core`, so an unpromoted Up Next
gets an Overflow row instead of relying on the Playlists segmented header.

**Not yet implemented.** The arithmetic is why:

- `TabLayout.capacity(for:)` is `5`, on iPad as well as iPhone, deliberately.
- `TabLayout.default` promotes all of `TabDestination.core`, exactly filling the
  bar, which is what makes "a user who never opens the setting sees no change"
  structurally true (ADR 0001, property 1).
- A sixth core destination makes `complement` non-empty, so `renderPlan` sets
  `needsOverflow`, More claims the last slot, and `visibleCount` drops to 4.

So the default bar cannot stay at five content tabs. **Which four ship as the
default is unanswered.** Slot order decides it, and today's order would push
Profile and Up Next into More.

A multiple-choice framing of that question was put to the user and declined —
they wanted to clarify something first, and the session ended before they said
what. Start there. Three constraints are worth naming as changeable, because any
of them dissolves the problem differently:

- **The five-item capacity.** Single source of truth in `TabLayout`, and
  deliberately not trait-dependent.
- **Up Next's existing home** in the `PlaylistsHostViewController` segmented
  header, which is the whole reason ADR 0001 classified it as extra.
- **Core vs extra** only controls whether an unpromoted destination gets an
  Overflow row. A destination can be promotable without being core — which is
  exactly what Up Next is today.

Whatever is decided, it touches `TabDestination.core`, `TabDestination.isCore`,
`TabLayout.default`, and ADR 0001's Consequences section, which already warns
that adding a core destination is a behavioural change for existing users.

## What the merge actually cost (read this before the next one)

The 17 conflict markers were the easy part and took an hour. **Five upstream
changes merged cleanly and broke the fork silently** — no conflict, no compile
error in some cases, just wrong behaviour or a late failure:

| Upstream change | Fork impact |
|---|---|
| `PlaybackManager.currentEpisode()` → property | 24 call sites |
| `PlaybackManager.playing()` → `isPlaying` | 5 sites, incl. a local alias `pm.playing()` that the first sweep missed |
| `PlaybackActionHelper` became `@MainActor` | `RadioPlaybackStarter` is reached off-main from intents and the widget; fixed with `Task { @MainActor in }`, not `assumeIsolated` |
| `PlaybackManager.init()` became `private` | Broke `RadioPlaybackControlsTests`; kept internal in the fork with a comment saying why |
| Mini player became a tab bar child (Liquid Glass) | 13 test failures and one production bug — see above |

Two more shape changes worth remembering: artwork moved into an aspect-fit inner
`artworkImageView` inside `episodeImage` (radio artwork had to be retargeted),
and `PlaylistDetailViewController` stopped being a `FakeNavViewController`, so
`PlaylistTabRootViewController`'s back affordance was rewritten against
`navigationItem`. `Strings+Generated.swift` is now build-phase generated and
gitignored upstream. `FeatureFlag.playlistsRebranding` is gone.

**Method that worked:** a throwaway `resolve.py` in the scratchpad that replaced
the Nth conflict block in a file from stdin, keyed on
`re.compile(r'^<<<<<<< .*?\n.*?^>>>>>>> .*?\n', re.S | re.M)`. And: when a test
count was wrong, probe the actual runtime values before theorising. Printing the
six view controller types is what identified the mini player in one shot.
