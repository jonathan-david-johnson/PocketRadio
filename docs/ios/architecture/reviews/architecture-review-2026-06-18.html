StationDetailViewController God Object → LyricSyncController STRONG
Files
Radio/StationDetailViewController.swift (697 lines) Radio/LyricsViewController.swift (424 lines) Radio/LyricsService.swift Radio/RadioFavoritesManager.swift
Problem

StationDetailViewController owns 8 responsibilities in 697 lines. The lyrics sync state machine alone is ~200: lyricStatus, lyricOffset, lyricTimer, lyricStartDate, lyricLines, currentLyricSongKey, currentLyricLineIndex, lyricFetchTask, lyricOffsetSaveTask. Then LyricsViewController duplicates the same state: its own timer, lineIndex, offset.

Deletion test: delete the lyrics block from StationDetailVC. Complexity reappears across both VCs — this is a real module waiting to exist. Interface ≈ implementation complexity. Shallow.

Solution

Extract LyricSyncController owning the full state machine: fetch, parse, timer, offset nudge, debounced Supabase persistence. Both VCs become thin consumers of one shared instance.

protocol LyricSyncDelegate: AnyObject {
    func lyricSync(_ c: LyricSyncController, didUpdateStatus: LyricStatus)
    func lyricSync(_ c: LyricSyncController, didUpdateOffset: TimeInterval)
}

class LyricSyncController {
    weak var delegate: LyricSyncDelegate?
    var currentOffset: TimeInterval { get }
    var currentStatus: LyricStatus { get }

    func load(artist: String, title: String, album: String?,
              playedAt: Date, stationId: String)
    func adjustOffset(by delta: TimeInterval)
    func stop()
}
Benefits
Locality — all lyrics logic in one module
Testability — state machine testable without loading any VC
Leverage — both VCs collapse to ~5 lines for lyrics
Eliminates duplication — LyricsVC no longer duplicates timer+offset

URL-Routing Parsers → TracklistParser Protocol STRONG
Files
Radio/RadioTracklistService.swift (193 lines) Radio/CuratedStation.swift Radio/curated_stations.json
Problem

RadioTracklistService.fetch() routes to a parser via URL.host.contains("kcrw") / "kexp". Adding a third station requires editing the service. The parsers (parseKCRW, parseKEXP) are concrete methods on the service — two adapters in disguise, with no seam named.

Deletion test: delete parseKCRW. Complexity doesn't vanish — it reappears for every new station. Two adapters are present; the seam just hasn't been named.

Solution
protocol TracklistParser {
    func parse(data: Data) throws -> [TracklistEntry]
}

struct KCRWTracklistParser: TracklistParser { ... }
struct KEXPTracklistParser: TracklistParser  { ... }
// Adding KQED = new file, zero service edits

extension CuratedStation {
    var tracklistParser: (any TracklistParser)? { ... }
}
Benefits
Locality — each station's quirks in one file
Leverage — service stays thin; station count doesn't grow it
Testability — each parser unit-testable with fixture JSON alone

// KQED → add another if, edit service

NotificationCenter Metadata Chain → RadioNowPlayingCoordinator WORTH EXPLORING
Files
Radio/RadioMetadataObserver.swift Radio/StationDetailViewController.swift Radio/RadioTracklistService.swift Radio/TrackArtworkResolver.swift
Problem

ICY metadata arrival triggers a 4-step pipeline across 4 files via untyped NotificationCenter posts. The debounce task and intermediate state (icyTitle, icyArtist) live in the VC. No single place describes "when now-playing changes, here's the full response." The notification userInfo is untyped — any subscriber can silently misread a key.

Solution
struct NowPlayingState {
    let artist: String; let title: String
    let tracklist: [TracklistEntry]; let artworkURL: URL?
}

class RadioNowPlayingCoordinator {
    var state: AnyPublisher<NowPlayingState, Never> { get }
    init(stationId: String, metadataObserver: RadioMetadataObserver)
}
Benefits
Locality — full now-playing pipeline in one testable class
Leverage — widget, mini-player, NowPlayingVC all consume same coordinator
Type safety — typed state replaces untyped userInfo dict

Split RadioFavoritesManager → LyricOffsetStore WORTH EXPLORING
Files
Radio/RadioFavoritesManager.swift (180 lines)
Problem

RadioFavoritesManager owns two independent concerns: (1) favorites — station IDs + ordering in radio_favorites; (2) lyric sync offsets — per-station integers in lyric_offsets. The only coupling: shared manager object. StationDetailViewController calls fetchLyricOffsets() and upsertLyricOffset() which have nothing to do with favorites. Two seams forced to share one object.

Solution

Extract LyricOffsetStore as a separate singleton. After Candidate 1 lands, LyricSyncController absorbs it — so StationDetailVC never directly calls either.

Benefits
Locality — offset bugs don't require reading favorites code
Single responsibility — each manager does one thing
Leverage — LyricSyncController absorbs LyricOffsetStore; VCs call neither

Manual Task Lifecycle → Structured TaskScope SPECULATIVE
Files
Radio/StationDetailViewController.swift
Problem

StationDetailViewController manually cancels 5 tasks and 1 timer across 4 lifecycle sites (viewWillAppear, viewDidDisappear, deinit, stopLyricTimer()). Forgetting any one path → task runs after view is gone.

Solution

A lightweight TaskScope container cancels all owned tasks on deinit. Most compelling after Candidates 1 and 3 land — evaluate then.

Speculative. Candidates 1 and 3 eliminate most manual cancellation naturally. Land those first.
Benefits
Safety — impossible to forget cancellation; structural guarantee
Locality — task ownership explicit and collocated
Top Recommendation

Start with Candidate 1 — LyricSyncController

Highest leverage: StationDetailVC shrinks ~200 lines, state duplication with LyricsVC disappears, the state machine becomes fully unit-testable, and it creates the natural home for Candidate 4's LyricOffsetStore. It's the prerequisite that makes the others easier.

Candidate 2 is the easiest standalone win — one afternoon, zero risk, immediate testability for all future station parsers.

Suggested order: 1 LyricSyncController → 2 TracklistParser → 4 LyricOffsetStore → 3 NowPlayingCoordinator → 5 TaskScope (if still needed)
