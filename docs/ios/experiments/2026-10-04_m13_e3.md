# M13 E3 — Network interception and the network guard

**Date:** 2026-10-04
**Result:** **PASS** (host-rewrite fixtures, Kingfisher loopback loads, and the guard all worked first run; inventory during real playback is clean)
**Code:** `pocket-radio-ios` worktree `pocket-radio-ios-carplay`, branch `spike/carplay-harness`, base `trunk` `0751918f8`. Spike code is uncommitted and disposable. No production file was changed.
**Simulator:** "PocketRadio CarPlay Tests", UDID `6565636E-BB8D-4C34-A9EB-56F2BB638400`, never signed in.
**Feeds:** The network design and the stub list in M13.1.

## Question

1. Can tracklist and iTunes requests be redirected to a fake world while keeping the real hostname, so the KCRW parser is still chosen?
2. Do Kingfisher downloads from `http://127.0.0.1` work?
3. What else touches the network during a scenario?

## Method

Test class `CarPlayOutputSpikeE3Tests`, two tests. Run with `make test_carplay_spike CARPLAY_TESTS=CarPlayOutputSpikeE3Tests`.

- **`SpikeNetworkGuard`** is a `URLProtocol`. It handles any `http(s)` request whose host is not loopback. A host with a fixture is answered from memory ("served"). Any other host is recorded and failed with `notConnectedToInternet` ("blocked"). Loopback requests pass through untouched. It is registered with `URLProtocol.registerClass` for `URLSession.shared` and added to `KingfisherManager.shared.downloader.sessionConfiguration.protocolClasses`, because Kingfisher owns a separate session.
- **Fixtures:** `tracklist-api.kcrw.com` returns a three-row KCRW JSON (song A with `albumImageLarge` pointing at loopback, song B with null images, one `[BREAK]` row). `itunes.apple.com` returns a result with `artworkUrl100` pointing at loopback.
- **`SpikeArtServer`** is an `NWListener` on loopback that serves solid-colour PNGs by path (`/art/red-…`, `/art/blue-…`) and can delay responses (`?delay=`). It is the artwork half of the fake world.
- **Test 1 (`hostRewriteKingfisherAndGuard`)** calls `RadioTracklistService.fetch`, then `TrackArtworkResolver.artworkURL` for song B, then retrieves both artwork URLs through Kingfisher into a throwaway cache and reads the centre pixel. It then sends one request to a non-fixture host on each stack to prove the guard catches leaks.
- **Test 2 (`inventoryDuringPlayback`)** plays the KCRW curated station through `RadioPlaybackStarter` with `prefetchTracklist: true` and `republishWidgetState: true` (E2 had both off), against the E2 ICY server, changes the title once, and logs every request the guard saw plus what `nowPlayingInfo` shows.

## Result

- **Host rewrite works, and the real hostname is kept.** `URLProtocol.registerClass` intercepts `URLSession.shared`. `RadioTracklistService` and `TrackArtworkResolver` need no change, and the KCRW parser was selected because the URL host is still `tracklist-api.kcrw.com`. The `[BREAK]` row was dropped, as in production.
- **iTunes fallback resolves from the fake.** Song B had no art, so the resolver asked `itunes.apple.com`, got the fixture, and upgraded `100x100bb` to `600x600bb`.
- **Kingfisher loads `http://127.0.0.1` images.** ATS does not block them. Both pixels read back as the expected colour.
- **Kingfisher ignores `URLProtocol.registerClass`**, as predicted. Setting `protocolClasses` on its `sessionConfiguration` works. The guard self-test shows a non-fixture host is blocked on both stacks.
- **The inventory during real playback is clean.** Only the two expected hosts were contacted. The signed-out simulator made no Supabase, sync, or analytics requests during the scenario.
- **Playback produced the right artwork end to end.** After the ICY change to `Song B-Artist B-Album B`, `nowPlayingInfo` showed title, artist, album of song B and blue artwork. That is the correct path, because the KCRW `Title-Artist-Album` ICY string parses to an artist and title that match a tracklist row. See "Implications for E7".

## Observations worth keeping

- **The tracklist was fetched once.** Only one `tracklist-api.kcrw.com` request occurred, at playback start. The ICY change did not refetch it. This confirms the "fetched in only two places" source reading: with no station detail screen open, nothing refreshes the tracklist.
- **`TrackArtworkResolver` init takes a session.** `TrackArtworkResolver(session:)` and `RadioTracklistService(urlSession:)` are injectable, but production uses the `.shared` singletons, which in turn use `URLSession.shared`. The host-rewrite approach therefore needs no production seam.
- **AVPlayer traffic is outside the guard.** The only audio host in these scenarios is the loopback ICY server (2 connections, as in E2). A scenario that played a non-loopback stream URL would reach the real network unseen. A scenario must only use loopback `streamUrl` values. M13.1 should assert that in its station factory.
- **Teardown log noise.** The `<<HLS-FASB>> signalled err=-15514` lines appear at `endPlayback` and in E2. They are AVFoundation messages during item teardown and did not affect results.
- **The fixture is a stand-in.** The tracklist JSON is hand-written in the shape documented in `RadioTracklistService.parseKCRW`; I did not diff it against a live response.

## Caveats

- **Wi-Fi was on.** The guard blocks `URLSession.shared` and Kingfisher traffic regardless, so a leak through those stacks would have failed and been logged. It does not cover AVPlayer, `NWConnection`/sockets used directly, or system daemons. The "Wi-Fi off" run the checkpoint asks for is still worth doing once at the end of M13, as the check that the whole suite works offline.
- **Signed-out simulator.** A signed-in account would add sync traffic. The dedicated simulator is meant to stay signed out.
- **One station, one scenario.** The inventory covers a single curated station with the prefetch and widget paths on. Other code paths (favourites, Discover) were not exercised.
