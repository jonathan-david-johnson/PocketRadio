# M13 E1 — Read back CarPlay-visible output

**Date:** 2026-10-04
**Result:** **PASS** (400/400 iterations across 20 separate test-host launches)
**Code:** `pocket-radio-ios` worktree `pocket-radio-ios-carplay`, branch `spike/carplay-harness`, based on `trunk` `0751918f8`. Spike code is uncommitted and disposable.
**Simulator:** "PocketRadio CarPlay Tests", UDID `6565636E-BB8D-4C34-A9EB-56F2BB638400`, iPhone 17 Pro, iOS 26.5. Created fresh for M13 and never signed in. Host: macOS 26.6.2, Xcode 27.0.
**Feeds:** probe design in M13.1; whether the favourite and mute buttons are in M13.2's scope.

## Question

Can a test read title, artist, album, `IsLiveStream`, media type, and the artwork **image** when the production code writes them from a main-queue hop? Is `CPNowPlayingTemplate.shared` button state readable in the test host?

## Method

Test class `CarPlayOutputSpikeE1Tests` (`PocketCastsTests/Tests/CarPlayOutputSpike/`), run with `make test_carplay_spike CARPLAY_TESTS=CarPlayOutputSpikeE1Tests`.

1. For each of 20 iterations, pick a solid colour (hue = i/20, full saturation). Build a 64×64 `UIImage` of that colour.
2. Hop `global → main` (the shape of `PlaybackManager.handleRadioTrackChanged`, which calls `DispatchQueue.main.async { NowPlayingHelper.setRadioTrackInfo … }`). On main, call `NowPlayingHelper.setRadioTrackInfo(stationId:trackTitle:artist:album:stationName:)` and `NowPlayingHelper.setArtworkImage(_:)`.
3. Read `MPNowPlayingInfoCenter.default().nowPlayingInfo` synchronously. Check title, artist, album, `MPNowPlayingInfoPropertyIsLiveStream`, `MPMediaItemPropertyMediaType == .music`, `MPNowPlayingInfoPropertyMediaType == .audio`, and that an `MPMediaItemArtwork` is present.
4. Call `artwork.image(at: 300×300)` and sample the centre pixel in sRGB. Pass if each channel is within ±2 and alpha is 255.
5. Separately, in `testE1_carPlayTemplateButtonState`, write and read `CPNowPlayingTemplate.shared` (`isUpNextButtonEnabled`, `isAlbumArtistButtonEnabled`, `updateNowPlayingButtons(_:)` → `nowPlayingButtons`) with no CarPlay scene connected.
6. To make "20 of 20 runs" mean 20 cold starts and not only 20 loop passes, repeat the whole test class in 20 separate `xcodebuild test-without-building` launches. Each launch starts a new test-host process.

## What this does and does not show

- **Shows:** a test in the host process can read back exactly what `NowPlayingHelper` wrote, including the artwork image through the request handler, with the production main-queue hop.
- **Does not show:** that iOS's Now Playing daemon or a head unit receives the same values. This reads the in-process dictionary and the app's own request handler. Head-unit rendering is out of scope per the M13 plan.
- **Template buttons:** the readback works on the shared template with no scene. Both properties round-trip, and `updateNowPlayingButtons` is reflected in `nowPlayingButtons`. This only proves the template stores what it is given. What `CarPlaySceneDelegate.updateNowPlayingButtons` computes is better asserted on its pure input: `CarPlayNowPlayingButtonSet.buttons(isLiveRadio: true, canMute: true, isMuted: false, isFavorite: true, …)` returned `[mute(muted: false), favorite(isFavorite: true)]`. That function is already unit-tested by `CarPlayNowPlayingButtonSetTests`. Driving the real `CarPlaySceneDelegate.setupNowPlaying()` was not attempted: it needs a `CPInterfaceController`.
- **Wi-Fi:** the host's Wi-Fi was **on** (`networksetup -getairportpower en0`). The M13 checkpoint says Wi-Fi off. This experiment makes no network calls. A simulator shares the host's network, so "Wi-Fi off" is a user-run step, not something a script should toggle on a shared Mac.

## Feeds

- **M13.1 probe design:** read `nowPlayingInfo` directly and sample artwork through `MPMediaItemArtwork.image(at:)`. Compare colours with a tolerance of at least 2/255. No snapshot or screenshot path is needed for artwork identity.
- **M13.2 scope (favourite and mute buttons):** the template's button *state* is readable and settable in the test host, so the buttons are *technically* in scope. Whether they should be is a scope decision for the user (D4), not an E1 finding. Cheaper coverage already exists through the pure `CarPlayNowPlayingButtonSet` function.
- **Viability:** the in-process approach is not blocked at the readback stage. Proceed to E2.
