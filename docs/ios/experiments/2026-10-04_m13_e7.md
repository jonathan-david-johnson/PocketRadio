## Question

Do H1, H2 and H3 reproduce in the spike harness on unmodified `trunk`?

## Method

Three scenarios, run in the real playback path (`RadioPlaybackStarter` → `PlaybackManager` → `AVPlayer`, an in-process ICY server, E3's fake tracklist/iTunes/artwork world, full reset between scenarios). The observed output is `MPNowPlayingInfoCenter.nowPlayingInfo`, sampled every 100 ms and logged on change, so each result has a timeline. The station is the curated KCRW Eclectic 24 UUID, so artwork resolution is enabled.

| Tag | Scenario | Expected by the spec |
|---|---|---|
| H1 | The tracklist is fetched once and lists only Song A (red). The stream announces A, then B. | After B, the display shows B and does not keep A's red artwork. |
| H2 | As above, then the listener pauses and resumes. | The display still shows A with red artwork. |
| H3 | The tracklist lists A (red, 25 s download) and B (green). The stream announces A, then B. | B's green artwork stays, even after A's slow download finishes. |

H1 and H2 delay the tracklist response by 2 s. That puts artwork resolution after the initial full info rebuild at playback start, which removes a start-up race (see "Extra finding" below). H3 sets Kingfisher's download timeout to 60 s, because the default 15 s would end the 25 s download early.

## Results

### H1 — stale tracklist keeps the previous song's artwork: **REPRODUCED**

Timeline from run 3 (the three runs are the same to within 0.1 s):

```
+ 0.10 s  title='KCRW Eclectic 24' artwork=rgb(7,9,7)      (station logo; tracklist not arrived)
+ 2.10 s  title='KCRW Eclectic 24' artwork=red             (tracklist arrives; top row resolved)
+ 9.02 s  ICY notification 'Song A'
+ 9.10 s  title='Song A' artwork=red
+14.66 s  ICY notification 'Song B'
+14.70 s  title='Song B' artwork=red                       <-- title is B, artwork is still A's
```

The runner then waited 8 s for any change. None came. Failure line: `carplay_artwork.feature:21: … Then the display does not show red artwork — display still shows red artwork (title 'Song B')`.

The mechanism matches the prediction. B is not in the cached tracklist, so `TrackArtworkResolver.bestResolveEntry` returns the cached top row (A). The key equals the last resolved key, so `lastResolvedRadioKey` suppresses resolution. The title updates by a different path, so the display shows B's text with A's picture. It needs a tracklist that has not been refreshed. In this harness nothing refreshes it, which is what happens when the phone never opens the station detail screen.

### H2 — a full rebuild replaces resolved artwork with the station logo: **REPRODUCED**

```
+ 2.10 s  title='KCRW Eclectic 24' artwork=red
+ 8.94 s  ICY notification 'Song A'
+ 8.95 s  pause()
+ 9.00 s  title='Song A' artwork=red
+10.51 s  play()
+10.66 s  title='Song A' artwork=rgb(7,9,7)       <-- logo; never restored
```

`rgb(7,9,7)` is the KCRW logo's centre pixel, confirmed separately with `UIImage(named: "kcrw_logo")` and `NowPlayingHelper.stationLogoImage`. The same song is still playing, and the display stays on the logo (the runner waited 8 s). The mechanism: resume rebuilds `nowPlayingInfo` (`setAllNowPlayingInfo`), which installs the logo, and the unchanged dedupe key prevents resolution from running again. Failure line: `carplay_artwork.feature:31: … Then the display shows the title "Song A" with red artwork`.

### H3 — slow artwork for an earlier song replaces the current song's: **NOT REPRODUCED** (lock-screen path)

```
+ 9.01 s  title='Song A' artwork=rgb(7,9,7)        (A's art still downloading)
+14.59 s  ICY notification 'Song B'
+14.60 s  title='Song B' artwork=green
          ... held for 14 s, past A's download completing at about +25 s ...
```

A's download did complete: the red image is stored in `radioAlbumArtCache` (logged: `stored in radio art cache=true`), and the art server logged both requests. The display stayed green. The guards in `resolveRadioArtworkForLockScreen` (`lastResolvedRadioKey == key` in both the URL and image callbacks) discarded the stale result. The scenario passed in all 4 runs.

Scope of this "not reproduced": only the `MPNowPlayingInfoCenter` write in `PlaybackManager`. The full and mini players and station detail each run their own resolution and were not covered (the milestone's out-of-scope list excludes them).

## Extra findings

1. **Start-up race (variant of H2).** In the first, undelayed E7 run, the same tracklist-then-rebuild order varied between scenarios in one session:
   - Scenario A: artwork was red at +0.10 s, then the initial rebuild replaced it with the logo at +0.20 s. It never came back, even after `Song A` arrived.
   - Scenarios B and C: the rebuild came first and resolution later, so red stayed.

   So whether artwork survives playback start depends on whether the tracklist response beats the first info rebuild. A cached tracklist (a second start of the same station in one app session) makes the bad ordering likely. This is why H1 and H2 delay the tracklist: it makes their results deterministic. The un-delayed form is flaky, which is consistent with "intermittent reports".

2. **Stale dedupe key across playback sessions** (from E4). `lastResolvedRadioKey` survives `endPlayback`. Stop and replay on the same song, and artwork resolution is skipped. Reproduced by the scenario pair in `CarPlayOutputSpikeE4Tests`.

## Caveats

- **Harness evidence, not device evidence.** Nothing here was observed on a phone or head unit. The harness reads `nowPlayingInfo`, which is what CarPlay draws from, but CarPlay's own rendering is out of scope.
- **The fake world picks the shape.** H1 requires the tracklist to lack the new song. Whether KCRW's real tracklist usually leads or lags its ICY title decides how often a user meets this. The milestone cites ICY lagging by 10–20 s, which would make the tracklist usually contain the new song and H1 rarer than here. Not measured.
- **Colour names, not images.** Equality is the centre pixel within 2/255.
- **H1/H2 use a 2 s tracklist delay** to remove the start-up race, which is itself a finding.
- **Sample size is small:** 3–4 runs each, all consistent.

## Feeds

- **D4 / M13.2:** H1 and H2 are the first two expected-failure scenarios. H3 can stay as a passing regression guard. The start-up race needs its own scenario: "a cached tracklist at playback start keeps the artwork".
- **`fix/stream-presentation`:** both bugs share the idea that a dedupe key outlives the artwork it vouches for. A fix has to make the key track what is actually displayed, not only what was last requested.
