# M13 E4 — Reset and isolation

**Date:** 2026-10-04
**Result:** **PASS**, with one finding that is a product bug candidate. Four `#if DEBUG` seams reset all the state that mattered. With them, results were independent of order (X→Y, Y→X, X→X, Y→Y). Without them, scenario 2 failed.
**Code:** `pocket-radio-ios` worktree `pocket-radio-ios-carplay`, branch `spike/carplay-harness`, base `trunk` `0751918f8`. Uncommitted and disposable. This is the first experiment that edits production files (four `#if DEBUG` seams, listed below).
**Simulator:** "PocketRadio CarPlay Tests", never signed in.
**Feeds:** The reset design in M13.1, and H1/H2 in E7.

## Question

Which process-wide state must be reset between scenarios? Can each reset be a `#if DEBUG` seam that leaves production behaviour unchanged?

## Method

Test class `CarPlayOutputSpikeE4Tests`. It reuses the E2 ICY server and the E3 fake world, and runs two scenarios in one process:

- **X:** ICY `Song A`, then `Song B`. Tracklist has A (red art) and B (no art). B's art therefore comes from the iTunes fallback (blue). Expected final artwork: blue.
- **Y:** ICY starts on `Song B`. Tracklist has B with direct art (green). Expected final artwork: green.

Y starts on the song X ended on. That is the case where stale dedupe state would show.

Tests:

| Test | What it does |
|---|---|
| `a_contaminationWithE2CleanupOnly` | X then Y, with only E2's cleanup between (pause, `endPlayback(saveCurrentEpisode: false)`, registry removal, clear `nowPlayingInfo`). Documents the leak. |
| `b_isolationWithFullReset` | X then Y, with the full reset (E2 cleanup plus the seams below) between. |
| `c_orderIndependence` | X→Y, Y→X, X→X, Y→Y, each with the full reset between steps and at the start. |
| `d_userDefaultsAndCarPlayFlag` | Diffs `UserDefaults.standard` across one scenario and reads `CarPlaySceneDelegate.isConnected`. |

A one-line state summary (current episode, queue, registry, `lastResolvedRadioKey`, tracklist cache, resolver key, `radioTrackStationId`, `nowPlayingInfo`) is logged at the start, after scenario 1, between scenarios, and at the end.

### Seams added (all `#if DEBUG`)

| File | Seam | Resets or reads |
|---|---|---|
| `podcasts/PlaybackManager.swift` (upstream) | `_resetRadioStateForTesting()`, `_lastResolvedRadioKeyForTesting` | `lastResolvedRadioKey` (`private`) |
| `podcasts/NowPlayingHelper.swift` (upstream) | `_resetRadioStateForTesting()`, `_radioTrackStationIdForTesting` | `radioTrackStationId` (`private static`) |
| `podcasts/Radio/TrackArtworkResolver.swift` (fork) | `_resetForTesting()`, `_currentKeyForTesting` | `NSCache`, `currentKey`, in-flight task |
| `podcasts/Radio/RadioTracklistService.swift` (fork) | `_resetForTesting()` | cache for all stations, failure-toast set. (An existing seam cleared one station's cache only.) |

Needing no seam: `RadioStationRegistry.remove(uuid:)`, `PlaybackManager.endPlayback`, `MPNowPlayingInfoCenter.nowPlayingInfo = nil`, and Kingfisher's public `clearMemoryCache()` / `clearDiskCache` on `radioAlbumArtCache`.

## Result

- **The E2 cleanup is not enough.** After it, `lastResolvedRadioKey`, the resolver's `currentKey`, `radioTrackStationId`, and the tracklist cache all keep scenario 1's values.
- **Scenario 2 failed without the seams.** It started on the title scenario 1 ended on. The artwork dedupe key matched, so `resolveRadioArtworkForLockScreen` returned early. There was no iTunes lookup, no artwork request, and no artwork swap. The final artwork was not green; it was some other image (pixel `rgb(7,9,7)`), which I did not identify but assume is the station or placeholder image.
- **The full reset fixed it.** With the four seams plus the existing public calls, results matched across all four orders.
- **Seams needed: four, in four files.** Two are in upstream files (`PlaybackManager`, `NowPlayingHelper`). Both reset `private` state, so they cannot move into a separate file's extension unless the properties are loosened to `fileprivate` or `internal`. That is an upstream-merge cost, as the milestone's risk section warned.

## Product finding (filed as [bug 5](../bugs/bug_5.md), symptom C)

`PlaybackManager.lastResolvedRadioKey` is never cleared when playback ends. In the app, if a user stops KCRW and starts it again while the same song is still playing, `resolveRadioArtworkForLockScreen` will see the same key and skip artwork resolution. The lock screen and CarPlay would then show the placeholder instead of the song's artwork. The test reproduces the mechanism, with `endPlayback` followed by a new `play()`.

Not yet shown on a real device or through the app's own stop button. The same stale key would also explain H2-style "artwork never recovers" reports. E7 reproduced the related pause/resume symptom; see bug 5.

## Other observations

- **Listening-stat keys change.** One playback scenario changed `StatsListenedTo`, `lastPauseTime`, and `lastPausedAt` in `UserDefaults.standard`. No keys were added or removed. The test host is the app, so these are the dedicated simulator's real values (see [bug 2](../bugs/bug_2.md) on this hazard). They are harmless on a signed-out dedicated simulator, but the M13.1 harness should either snapshot and restore them or document that they drift.
- **`CarPlaySceneDelegate.isConnected` was untouched** by playback. It is `private(set)` with an existing `setConnectedForTesting(_:)` seam, so scenarios that need CarPlay connected (the `setRadioAlbumTitle` suppression) can drive it without a new seam. A reset should set it to `false`.
- **`widgetRepublisher` was off** (`republishWidgetState: false`). E3 ran it on once. It writes App Group state, which is outside the process and which E4 did not diff. M13.1 should stub it or leave it off.
- **`RadioPlaybackStarter.play` sets `AnalyticsPlaybackHelper.shared.currentSource`.** This is more process-wide state. It did not affect any output, so I did not reset it.
- **Cost.** Each scenario takes roughly 10–20 s, mostly the ICY title wait. The suite of four tests (about 10 scenario runs) took 92 s.

## Caveats

- Two scenarios. The state list comes from reading the code plus the observed leaks. Some state I did not enumerate may exist, for example in `LyricsService` (it has its own LRU store) and the lyric controllers, which these scenarios never start.
- Equality was judged on title and the artwork's colour name only. Album and artist were logged in E3 but not compared here.
- Single run of each order. E5 is where repeat-to-repeat stability is measured.

## Feeds

- **M13.1 reset:** `fullReset()` in `CarPlayOutputSpikeE4Tests` is the starting point. It touches seven pieces of state; four need seams.
- **E7:** the stale-key finding gives H1/H2 a ready mechanism to test. Y is the shape of the scenario.
