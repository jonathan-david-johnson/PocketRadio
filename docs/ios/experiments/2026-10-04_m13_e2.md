# M13 E2 — Real playback inside the test host

**Date:** 2026-10-04
**Result:** **PASS** (6/6 launches: playback reached, 4/4 titles observed each time, no restore, no autoplay)
**Code:** `pocket-radio-ios` worktree `pocket-radio-ios-carplay`, branch `spike/carplay-harness`, based on `trunk` `0751918f8`. Spike code is uncommitted and disposable. No production file was changed.
**Simulator:** "PocketRadio CarPlay Tests", UDID `6565636E-BB8D-4C34-A9EB-56F2BB638400`, iOS 26.5, never signed in. Host: macOS 26.6.2, Xcode 27.0.
**Feeds:** D1 (input tier) and D2 (fake-world placement).

## Question

Inside the test host, does `RadioPlaybackStarter` → `PlaybackManager` → `AVPlayer` reach the playing state against a localhost ICY stream? Do ICY titles reach `radioStationNowPlayingDidChange`? On a fresh, signed-out simulator, does launching the test host restore or autoplay another episode?

## Method

Test class `CarPlayOutputSpikeE2Tests` (`PocketCastsTests/Tests/CarPlayOutputSpike/`), run with `make test_carplay_spike CARPLAY_TESTS=CarPlayOutputSpikeE2Tests`.

1. **Fake world, in process.** `SpikeIcyServer` is an `NWListener` bound to the loopback interface on an ephemeral port. It serves `tone_128k.mp3` (10 s, 440 Hz, mono, 128 kbps CBR, amplitude 0.05; generated with `ffmpeg … libmp3lame`) in a loop. It answers `HTTP/1.0 200 OK` with `icy-metaint: 8192` when the request has `Icy-MetaData: 1`. It sends a 48 000-byte (~3 s) burst and then paces at 16 000 B/s. It inserts a `StreamTitle='…';` block at the next metaint boundary after `setTitle(_:)`.
2. **Station.** `RadioStation(stationId: "6238f5e8-a9ee-4c88-9713-2d1ab4112ac9", name: "KCRW Eclectic 24", streamUrl: "http://127.0.0.1:<port>/stream", tracklistUrl: <curated KCRW URL>, logoAsset: "kcrw_logo")`. That UUID is KCRW's `defaultSeedUUID` in `curated_stations.json`; the test confirmed `CuratedStationsLoader.enhancementsByUUID[uuid] != nil`. Started with `RadioPlaybackStarter.shared.play(station:source:.unknown, prefetchTracklist: false, republishWidgetState: false)`. The prefetch and widget republish are off so that nothing but the loopback server is contacted.
3. **Titles.** The stream starts with `Song 0-Artist 0-Album 0` (the KCRW `Title-Artist-Album` shape that `RadioMetadataObserver.parseUnspacedTriple` handles). The test then changes the title three times (`Song 1`, `Song 2`, `Song 3`), each only after the previous one was observed.
4. **Playing state.** `PlaybackManager.isPlaying && !isBuffering` and `currentTime()` advanced by at least 1.0 s. (`isPlaying` alone is true as soon as `aboutToPlay` is set, so it cannot prove audio is flowing.)
5. **Latency.** `systemUptime` just before the server hands the metadata block to the socket, to `systemUptime` inside a `NotificationCenter` observer for `radioStationNowPlayingDidChange` (queue `.main`).
6. **Readback after each title.** After 0.3 s, read `MPNowPlayingInfoCenter` to see what the production main-queue hop wrote.
7. **Fresh host.** At test start, and again after 3 s idle, log `currentEpisode`, `isPlaying`, and `upNextCount`. This is a separate fresh launch each time: the first launch is `make test_carplay_spike`, and launches 2–6 are `xcodebuild test-without-building` (same test code, no rebuild).
8. **Cleanup.** `pause()`, `endPlayback(saveCurrentEpisode: false)`, registry removal, clear `nowPlayingInfo`. Without it, the next launch would see a queued radio shim and the fresh-host check would be contaminated.

## Result

- Playback reached the playing state in every launch, at 3.38–3.58 s after `play()`.
- Every title (4 of 4, in each of 6 launches) arrived as `radioStationNowPlayingDidChange` with title, artist, and album split correctly by the KCRW parser.
- Each notification also produced the correct `nowPlayingInfo` title, artist, and album through the production `DispatchQueue.main.async` hop, with `IsLiveStream = 1`.
- The host did not restore or autoplay anything on launch.
- The in-process server did not fail, so the **out-of-process Python fallback was not needed** and not tried.

**E2 passes.**

## How to read the latency number

The 5.2 s is **not** the processing cost of the app's pipeline. It is dominated by where the server places the metadata block relative to the playhead.

- AVPlayer delivers timed metadata when playback reaches the block in the stream, not when the bytes arrive.
- The spike server writes the block when it is ~3 s of burst plus the player's own read-ahead in front of the playhead.
- The values barely move between launches (spread 0.07 s). That is consistent with this reading but does not prove it; I did not vary the burst size to confirm. Treat the explanation as an inference.

What the number does establish: a scenario must wait **about 5 s of real time per title change** when it feeds a real stream. A scenario with 3 changes costs ~15–25 s. That is the number E5 needs for the cost estimate, and it is the main input to D1. A smaller burst would lower it, but a real station's lead is set by the station, so the spike keeps a realistic 3 s burst.

## Observations worth keeping

- **AVPlayer opens two connections.** Connection 1 is `Range: bytes=0-1` with no `icy-metadata` header (a probe). Connection 2 is the real stream with `icy-metadata: 1`. The fake server must therefore tolerate a probe, and metadata is only on the second connection. The spike server answered the probe like any other request (200 with audio, no metadata), and playback was unaffected. I did not record when or whether the probe connection closed.
- **User-Agent is `Pocket Casts`.** A fake server can key on it.
- **ATS permits `http://127.0.0.1`.** `NSAllowsArbitraryLoads` is true in `podcasts-Info.plist`, so no plist change was needed.
- **The tracklist and artwork paths did not run.** With `prefetchTracklist: false` and an empty tracklist cache, `TrackArtworkResolver.bestResolveEntry` had nothing to resolve. This is E3's territory.
- **Audio session activation works in the test host.** Playback reached the playing state, so `activateAudioSession` did not block it.

## Caveats

- **Wi-Fi was on** (`networksetup -getairportpower en0`). The M13 checkpoint wants it off. E2 binds only to loopback and disables the tracklist prefetch, but I did not capture traffic to prove nothing else left the machine. E3's network guard is the right tool for that claim.
- **The sample is small and highly regular.** Six launches, one fixture, one bitrate, an idle main thread. "Main-thread contention" was not stressed: the test spins the run loop while waiting, and the server lives on its own queue. E5 (50 runs) is where flakiness shows up, and a scenario that does heavy UI work on main while the stream runs is untested.
- **Mono 128 kbps MP3 only.** KCRW's real stream is AAC, and `streams.kcrw.com` may be HLS with ID3 metadata instead of ICY. The ICY path is proven; the HLS path (per the menubar M11 experiments) is not covered here.
- **The tone plays through the simulator's audio output** at amplitude 0.05. I did not check whether it was audible on the Mac.

## Feeds

- **D1 (input tier):** a real ICY stream is viable in the test host: 6/6 launches, with no failures. The cost is ~5 s of real time per title change plus ~3.5 s to start. E5 decides whether that cost is acceptable for ~15 scenarios. A metadata-injection seam is still the cheaper tier for scenarios about artwork or tracklist logic.
- **D2 (fake-world placement):** in-process Swift (`NWListener`) works. Recommend it over out-of-process Python: no extra process, no `TEST_RUNNER_` port plumbing, and the fixture is in the test target. Revisit only if E5 shows main-thread contention.
