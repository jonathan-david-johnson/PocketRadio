# M13 E6 — Gherkin runner for iOS

**Date:** 2026-10-04
**Result:** A minimal in-bundle runner (156 lines) meets all five checks. No third-party runner was built or run, so the comparison is incomplete: the library side rests on repository metadata only.
**Code:** `pocket-radio-ios` worktree `pocket-radio-ios-carplay`, branch `spike/carplay-harness`, base `trunk` `0751918f8`. Uncommitted and disposable.
**Draft spec:** `contracts/features/now_playing/carplay_artwork.feature` in the shell (**uncommitted**, as planned until D3).
**Feeds:** D3.

## Question

Which runner turns shared `.feature` files into XCTest results: a minimal in-bundle Gherkin parser, or a maintained Swift Cucumber library?

## Method

1. Drafted the H1, H2 and H3 scenarios as one feature file with platform-neutral wording ("the system now-playing display shows…"), tags `@ios @carplay` and `@h1`/`@h2`/`@h3`.
2. Built option A, a minimal runner, in the test target:
   - `SpikeGherkin.swift` (156 lines): parser (Feature, Background, Scenario, tags, Given/When/Then/And/But, line numbers), a regex `StepRegistry`, and `GherkinFeatureCase`.
   - `GherkinFeatureCase` overrides `defaultTestSuite`. For each scenario it adds an Objective-C method with `class_addMethod` and a block, named `scenario_<tags>_<slug>`, and registers an `XCTestCase(selector:)` for it.
   - Failures are recorded as an `XCTIssue` with a source location in the `.feature` file, so Xcode and `xcodebuild` print `…carplay_artwork.feature:21: error:`. The message includes the Swift step definition's file and line.
   - The feature file is located from `#filePath`, going up to the worktree and then to `../contracts/`, as `RemoteCommandFixtureTests` does for `contracts/remote/`.
3. Implemented the steps (`CarPlayArtworkFeatureTests.swift`, about 170 lines) on top of the E3 and E4 plumbing. These steps are the E7 baseline.
4. Ran the five checks. For option B (a maintained library), I looked up repository metadata for two candidates but did not add or run either.

|---|---|---|

| `-only-testing:` selects one scenario | **Yes** | `-only-testing:PocketCastsTests/CarPlayArtworkFeatureTests/scenario_h3_slow_artwork_for_an_earlier_song_never_replaces` ran exactly that one test (1 executed, 1 passed) even though the method is registered at runtime. |

| An undefined step fails loudly | **Yes** | Probe feature `SpikeProbe.feature`: `SpikeProbe.feature:4: error: … UNDEFINED STEP: When the listener does something nobody defined`. The run stopped at that step and the scenario failed. |
| Cost | **156 lines, no dependency** | Plus about 170 lines of step definitions for three scenarios (these are needed with any runner). |

Limits of option A as built:

- No Scenario Outline, Examples tables, doc strings, data tables, `Rule`, or hooks. Tags are parsed but not used to filter. None were needed by S1–S7's draft wording, but a larger suite may want Scenario Outline.
- Step matching is first-match regex. Ambiguous matches are not reported.
- Scenario names become method names, truncated to eight words. Two scenarios with the same first eight words would collide. Use unique leading words, or add the tag, which the name already includes.
- Failures carry the step text but Xcode's issue navigator only shows one line per scenario, because the runner stops at the first failing step.
- The dynamic registration depends on `XCTestCase(selector:)` and `class_addMethod`. It worked on Xcode 27 and iOS 26.5. It is the part most exposed to a future XCTest change.
- The Xcode test navigator (GUI) might not list dynamic methods before a run. I used only `xcodebuild`. Not checked in the IDE.

## Wording check for other platforms

The steps read in terms of the listener, the stream, and "the system now-playing display". Nothing names `MPNowPlayingInfoCenter`, CarPlay, or iOS. The Android Auto equivalent of "the display" is the media session metadata; the menubar equivalent is the menu bar title. The step `the station's tracklist takes 2 seconds to arrive` and `… artwork that takes 25 seconds to download` describe the fake world, which each platform would also need to be able to stage. Those are the steps most likely to need a platform-specific harness.

## Feeds

**D3 (runner).** Evidence favours the **minimal in-bundle parser**: it passes all five checks at 156 lines and has no dependency. The only maintained-library candidate I found (Cucumberish) is stale and was not tested. If the suite later needs Scenario Outline or tag filtering, extend the parser, or revisit with a real trial.
