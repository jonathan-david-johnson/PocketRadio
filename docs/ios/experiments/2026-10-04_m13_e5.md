# M13 E5 — Determinism and cost

**Date:** 2026-10-04
**Result:** **PASS** — 50/50 scenarios correct, with a spread of 0.2 s across all runs. One environment hazard found: the host Mac's sleep breaks audio. Wrap runs in `caffeinate`.
**Code:** `pocket-radio-ios` worktree `pocket-radio-ios-carplay`, branch `spike/carplay-harness`, base `trunk` `0751918f8`. Uncommitted and disposable.
**Simulator:** "PocketRadio CarPlay Tests", never signed in. Wi-Fi on.
**Feeds:** D1 (input tier) and the run-time budget for M13.1/M13.2.

## Question

Is an end-to-end scenario stable enough to gate a merge? What does it cost?

## Method

`CarPlayOutputSpikeE5Tests.testE5_repeatedScenarios`. One process, 50 scenarios, alternating two kinds, with the E4 full reset before the first and after every one. Each scenario runs real playback (ICY stream from the in-process server), the E3 fake tracklist, iTunes and artwork world, and checks the final artwork colour.

- **X (25 runs):** the stream starts on `Song A`, then changes to `Song B`. Song B has no tracklist art, so artwork comes from the iTunes fallback. Expected: `Song B` with blue artwork.
- **Y (25 runs):** the stream starts on `Song B`, whose tracklist row has green art. Expected: green.

Fixed waits: playing state within 30 s, each title within 45 s, artwork within 8 s. Run with `caffeinate -dimsu make test_carplay_spike CARPLAY_TESTS=CarPlayOutputSpikeE5Tests`. A short run: `TEST_RUNNER_SPIKE_E5_RUNS=4`.

| Kind | Runs | Mean | Min | Max |
|---|---|---|---|---|
| X (initial title, then one change) | 25 | 9.00 s | 8.9 s | 9.1 s |
| Y (initial title only) | 25 | 3.30 s | 3.3 s | 3.3 s |

Every run ended on the expected artwork. The 0.2 s spread is smaller than E2's, because the waits here end when the display changes, not on a fixed timeout.

## Cost estimate for about 15 scenarios

- **Per scenario:** about 3.3 s to start and show the first title, plus about 5.7 s for each further title change. A scenario with two title changes is about 15 s. The three E7 scenarios took 17–29 s each because they also wait for settle periods (8 s) and a 14 s hold.
- **Suite of 15:** roughly 3–5 minutes of test time, plus an incremental build and simulator boot of about 1–2 minutes when nothing is cached. Estimates, not measured on a 15-scenario suite.
- **Launch overhead:** the 50 runs shared one launch. A one-scenario-per-launch design (as in E2) adds the launch cost to every scenario; I did not measure it in this experiment.

## Environment hazard: the host's sleep breaks real playback

Two earlier attempts at this experiment failed for a reason unrelated to the app:

```
AQMEIO.cpp:201   timed out after 15.000s
AQME Default-InputOutput: client stopping after failed start
[PlaybackManager] Playback did fail with error: ... (CoreMediaErrorDomain error -66681.)
```

The log timestamps jump by minutes (for example 13:47 → 14:00), and `pmset -g log` shows `Entering Sleep state due to 'Maintenance Sleep'` on the host at the same times. The simulator's audio output depends on the host's audio device. When the Mac goes into maintenance sleep mid-run, playback fails to start, ICY titles never arrive, and scenarios time out. Restarting the simulator did not help. Running under `caffeinate -dimsu` fixed it, and then all 50 runs passed.

This is a host-environment requirement, not a test flake in the usual sense: **the harness target must hold the machine awake** (`caffeinate -dimsu` around `xcodebuild`). Without that, a run started while the user steps away can fail. Those failures do look like product failures ("title never arrived").

## Result

- **Determinism is good for the real-stream path.** 50/50 correct, timing within 0.2 s, on an awake host.
- **No flakiness from AVPlayer, the in-process server, or main-thread contention** was seen in these runs. The test spins the main run loop but does no heavy UI work, as in E2.
- **Reset overhead is negligible** next to the stream waits.

## Caveats

- **Short scenarios.** Both kinds are simple. E7's longer scenarios ran only 3 times each (see its report), not 50.
- **Awake host only.** Also one machine, one Xcode, one simulator runtime (iOS 26.5), and low background load (load average fell from 15 to 7 during the incident, which I did not isolate as a factor).
- **Wi-Fi was on.** Nothing in the scenario depends on it, and the E3 guard saw no unexpected hosts, but the "offline run" is still outstanding.
- **Single-process reset.** If one scenario hangs or crashes, the rest are lost. A runner that isolates scenarios would pay launch cost per scenario.

## Feeds

**D1 (input tier).** The evidence supports **real ICY streams for every scenario**, not a metadata-injection seam:

- Real playback was stable (50/50) and the cost is modest (about 5.7 s per title change).
- An injection seam would exercise a different code path from the one users hit. The E7 findings (artwork lost on pause/resume and on start-up) depend on real playback timing and would not appear with injected metadata.
- Keep an injection tier as an optional shortcut only for scenarios that are purely about tracklist or artwork logic and need many title changes.

M13.1 must add the `caffeinate` wrapper to its Make target.
